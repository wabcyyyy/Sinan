## 确认的问题与优先级

### P1：类别证据把“不知道”当成“不属于”，可放行被排除的寺庙

触发：用户排除 `temple`，条目名 `浅草寺`，类别字段仅有 `amenity=place_of_worship`，没有 `religion`。预期是保持阻断或未知，实际从无证据时的 `violation` 变成 `pass`。仅有 `tourism=attraction` 同样通过；`unverified`、`stale` 的类别字段也会被采用。

已用生产检查函数复现，见 [规则回放](current-state-review-2026-10-12/rules.json)。根因在 [constraint_checks.py](../../travel-agent-python/app/agent/generation/rules/constraint_checks.py:84) 和 [排除判定](../../travel-agent-python/app/agent/generation/rules/constraint_checks.py:156)：只解析字段键，不检查证据可信度；只要存在任何标签且未正向命中排除类别，就推翻名称判据。缺少宗教标签并不是非寺庙的正向证据。这是规则级已确认回归，本轮未声称真实生成恰好安排了浅草寺。

建议先修三态判定与证据资格：只有足够、可信的非目标类别证据才能推翻名称判断，缺失和过期证据不能放行。

### P1：金额大小不能证明币种，费用兜底会错误压低人民币价格

触发：东京 `food` 条目，`cost=1500`，备注明确为“人民币估算”。生产 `sanitize_itinerary_items` 实际改成 `72`，并追加“原估价为日元”的断言。`1000` 保持原值，`1001` 却变成 `48`。相同人民币单位下，超过阈值一元会让金额骤降约二十倍。

根因在 [fx.py](../../travel-agent-python/app/agent/data/fx.py:230)：根据目的地和数值范围推断币种，输入本身没有币种证据。这个行为会同时影响展示和预算检查。无预算时补上 CNY 提示是合理修复；这种无证据自动换算不可靠。复现见 [规则回放](current-state-review-2026-10-12/rules.json)。

建议依据明确币种来源换算；来源未知时保留不确定性并修复模型输出，避免把猜测写成事实。此项是合成边界输入复现，不是声称本轮行程已实际误算了这笔餐费。

### P1：慢 Overpass 查询使整个餐饮域丢失，严格模式继续失败

行程 22 真实日志记录 `search_foods 超时（>10s）`，随后 Overpass 两次 504。当前 [search_foods](../../travel-agent-python/app/agent/tools/impl.py:151) 在取其它餐饮池前串行等饮食池，工具总预算只有 10 秒，而 [Overpass 客户端](../../travel-agent-python/app/agent/data/overpass.py:34) 至少等待 25 秒且重试一次。结果是调用方丢失整份餐饮研究，而非只丢失 diet 标签；超时线程仍继续执行。失败负缓存又可保持 600 秒。

22 号最终两餐为“新宿三丁目 素食餐厅”“新宿站西口素食咖啡店（豆乳甜品与轻食）”，没有实体 ID 或饮食依据，只是缺少具体店名的候选描述。23 号严格模式四餐都无饮食依据，失败符合交付门的保护行为，但核心需求没有完成。不能用放松严格门槛来解决。

同一运行日志还确认：当前 search 角色走 DeepSeek 通道，没有联网搜索插件，联网补池与实时价已经明确降级。名义上的“联网搜索”在这套运行配置下没有实际补证能力。

建议先隔离饮食补证失败，保住其它已取得的餐饮实体数据，统一外部请求/工具/研究层的时间预算与失败缓存语义，并恢复可工作的联网搜索配置。单纯延长等待或继续修改生成提示不足以保证成功。

### P1：真实内容仍有可执行性错误，餐饮类型还可能被景点类型覆盖

22 号把都厅南展望台写成“9:30–17:00，周一休”，实用提示又重复“周一休馆”。截至本轮核查，[东京都财务局官方说明](https://www.zaimu.metro.tokyo.lg.jp/tochousha/goannai/tenbou/)给出的南展望室通常入室时间是 9:30–21:30，定期休室为每月第一、第三个周二，节假日有顺延等例外。生成结果混淆了南北展望室口径；“待核实”徽标不能消除具体错误。

旧样本 21 中 `Kyubei Sushi at Keio Plaza Hotel` 被列为 `attraction`，备注却描述预约、套餐及素食需求；因此计入第三个景点，却不进入只检查 `food` 的饮食规则。22 号第二天也保留了相同条目类型。观察到的类型错配与 [参考池落地](../../travel-agent-python/app/agent/generation/content/reference_pool.py:249)直接用候选检索类别覆盖模型用途的实现一致；应继续追踪该实体原始类别/候选重叠以确认完整归因，不能把每个“餐厅”字样都机械改成 food。

建议核对真实类别证据和条目用途，避免通过类型错配遗漏一餐的饮食检查；营业时间/闭馆日缺证据时不输出确定规则。当前仅核查这一条官方事实，未声称其余事实均正确。

### P1：入口抽取仍会退化为空，普通用户需要重复输入

第一次本轮 `/clarify` 对完整输入返回空需求字段，后端记录 JSON 解析失败。随后重新提交原话成功，继续生成 22/23；独立真实调用又观察到一次空字符串、一次合法 JSON。见 [真实抽取响应](current-state-review-2026-10-12/extractions.json)、[原始输出形状](current-state-review-2026-10-12/clarify-raw.json)和 [运行日志](current-state-review-2026-10-12/runtime.log)。

[clarify._ask](../../travel-agent-python/app/agent/editing/clarify.py:172)要求模型输出 JSON，但调用未设置 JSON response format；解析失败没有有界修复重试，直接进入降级空槽位。降级提示避免了假装成功，抽取稳定性仍未解决。本轮样本很小，不据此估算总体失败率；也没有证据确定所有坏输出都是 token 截断。

## 对上一轮根因判断的修正

最新饮食报告把 21 号失败重点怀疑为“分店后缀与权威名键不一致／证据挂载晚于判定”。本轮把其实际交付字段回放给生产检查器：`Délifrance` 与 `くら寿司` 的饮食检查都为 `pass`；第一天硬阻断是三个景点超过上限，第二天是活动 210 分钟低于 240 分钟。

同时 DB 的旧失败文本确实用了另一次尝试中的分店名。流式草稿先落库、后续修复失败只更新错误状态而保留旧条目，足以解释“页面当前条目与最后错误名称不同”，不能只凭这个差异确定发生了证据挂载时序错误。需要按同一次 attempt 关联原始输出、落地、校验和写库事件后再归因；**该时序缺陷当前证据不足，无法确认**。
