# 独立规划 worker 与故障恢复

整趟规划和自动恢复由 `worker.py` 执行，API 提交后立即返回行程 ID。两者复用同一套 Python 业务代码和 `plan_days`，MySQL 是任务、交付和累计预算的权威；没有引入消息队列。
单日重生成、聊天编辑、导出仍沿用现有业务入口。本轮不宣称所有模型调用都已移出 API。

## 本地启动

先按 [开发指南](development.md) 配置环境并启动 MySQL/Redis，再开三个终端：

```bash
# API：先完成启动迁移，再启动 worker
cd travel-agent-python
uv run python main.py
```

```bash
cd travel-agent-python
uv run python worker.py
```

```bash
cd travel-frontend-react
npm run dev
```

`just dev`、`just worker`、`just dev-fe` 对应上述入口。完整本地 Compose 的 `--profile apps up` 同时启动 API、worker 和前端；只启动 API 时，已接受的规划保留在数据库中等待 worker，不会在 API 中偷偷执行。
API 与 worker 必须使用相同数据库、模型路由、加密配置和时区。此阶段以同一宿主机为范围，两个进程共用 `data/`（Compose 已挂同一路径）；LangGraph 检查点仍是本地 SQLite。worker 不运行 DDL，启动前应先由 API 完成迁移。

## 执行与恢复规则

1. 行程主表、日期和 `planning_task.request_json` 在同一事务提交；登记任务失败时全部回滚。
2. API 登记 `QUEUED`，不申请执行租约。全局容量默认 8（含执行和排队），检查与入队由数据库锁串行化；同用户任务检查也使用数据库行锁。超额返回 429，事务回滚，不留行程壳。
3. worker 默认最多处理 4 个任务，只领取当前能执行的工作。MySQL `FOR UPDATE SKIP LOCKED` 支持多个 worker 竞争领取，执行模型时不持领取事务。
4. 领取后复用租约、心跳、取消、绝对截止、累计消耗与旧执行者保护。排队时间计入原截止期；接管不重开时间窗或调用额度。
5. 每次出现空槽，先按提交顺序检查过期持有者，再领取新任务；正常未领取任务不进入恢复分支。满载时仍每 10 秒扫描，收敛过期与取消任务。持久任务以租约过期为依据，不再额外等待行程闲置 5 分钟；已成功日期保留。默认租约 90 秒，实际接管时间还受可用执行槽、轮询和剩余截止期影响。
6. 过期任务停止后续模型调用并收敛为失败或部分交付；取消任务不自动复活。

`PLANNING_WORKER_CONCURRENCY` 可在 1–4 内调整，默认 4；`PLANNING_QUEUE_CAPACITY` 默认 8，单 worker 默认最多一批运行、一批等待；`PLANNING_POLL_SECONDS` 默认 1。降低并发时应相应收紧总容量。增加进程会增加模型请求、数据库连接和外部服务调用，当前没有真实供应商的全局吞吐测量或共享模型配额。
worker 收到停止信号后停止领取并等待已有任务；容器宽限 330 秒，超过宽限由容器终止，剩余责任通过租约恢复。API 的 `/healthz` 不代表 worker 正常。Compose 为 worker 配置独立健康文件，只有成功轮询数据库后才刷新；健康检查允许一次完整任务截止期与租约窗口，支持检查点恢复占用轮询线程，不能据此证明容量。还应查看 worker 日志、QUEUED 堆积和租约更新。

## 跨实例 SSE

业务生成事件写入 MySQL `generation_event`，同一行程在行锁内分配序号并提交，避免并发发布时游标跳过尚未提交的较早事件。API 每 0.5 秒读取新事件，客户端持 `Last-Event-ID` 可连接任一 API 实例。
每个行程最多保留 256 帧，记录保留 2 小时；日志缺口发 `resync`，终态仍从业务库补帧。聊天私有流不进入共享回放。连接数限制仍按 API 进程计数，本轮没有实现全局连接配额。
详情缓存先核对数据库中的规划修订、生成事件版本与状态；即使 Redis 不可用，API 的本地缓存也不会把 worker 已交付结果显示成旧的生成状态。
这是小规模本地运行的实现，增加了数据库读写；没有用吞吐或延迟改善来包装这个取舍。

## 可复现故障验收

在后端目录运行：

```bash
uv run python scripts/verify_planning_worker.py
```

脚本使用当前 MySQL 连接创建随机 `sinan_worker_probe_*` 临时库，只对该库执行迁移，退出时删除该临时库。账号须有建库和删库权限；不要给线上应用账号增加该权限。日志与检查点放入临时目录。
模型输出使用 fixture，禁止外部 HTTP；费用计数是合成输入，不是供应商账单。验收使用真实 HTTP API、独立 worker 进程、MySQL 事务和操作系统进程终止，覆盖：

- API 已接受任务后退出，worker 仍能交付。
- 第一天提交后终止 worker，两个 worker 竞争接管，已交付条目 ID 保持不变。
- 接管继承截止期与累计消耗，旧令牌条件更新被拒，只产生一次最终交付事件。
- 从另一 API 实例带游标补发，事件不重复、按序且能够结束；原 API 在 Redis 不可用时也能读到完整交付。

验收将租约缩短到 3 秒、心跳 1 秒，保留 10 秒扫描间隔，加快故障实验。测得的恢复时间仅对应这组配置，不能当作默认 90 秒租约的恢复承诺。
2026-10-22 Windows 本机 MySQL 实验中，上述八项检查通过；从终止 worker 到恢复交付观测为 3.938 秒。新 worker 启动时会立即检查一次，之后按 10 秒扫描。这是一轮固定输出的功能验收，未做恢复时延分布或吞吐测量；CI 会在 Linux/MySQL 上执行同一脚本。
这不证明真实模型质量、供应商计费恰好一次、跨宿主机高可用、数据库故障容错或高并发容量。公开固定演示仍不连接真实后端。

## 本地假模型 HTTP 负载实验（2026-10-22）

`scripts/verify_planning_load.py` 复用上述临时库、真实 API 与独立 worker。研究策略与行程内容固定，禁用交付后的富化；模型请求经真实 `LLMClient` 访问本地 OpenAI 兼容 HTTP 服务，覆盖普通请求、SSE、重试、用量预留/结算和产品落库。非该服务的 HTTP 一律拒绝。它没有执行完整研究图或真实模型，不量测供应商能力。

实验先约定：使用两个 API、多用户；突发受理期间暂停假模型响应，避免任务提前完成掩盖超额准入。完整交付同时要求业务 `COMPLETED`、执行 `FINISHED`、全部日期 `SUCCEEDED`。报告分别列出受理、429、业务/执行状态、从提交到首次模型请求的等待及从提交到终态的耗时；等待分位数只统计实际开始过模型请求的任务，未开始数另列。一次观测的分位数不作线上 SLO。

Windows 本机、同 MySQL 与固定响应策略，8 次提交、容量 8、截止 30 秒、每个日计划 HTTP 响应延迟 0.35 秒：

| 执行槽 | 完整交付 | 交付 p95（秒） | 观测 HTTP 请求数 |
| --- | --- | --- | --- |
| 1 | 8/8 | 9.844 | 24 |
| 2 | 8/8 | 6.553 | 24 |
| 4 | 8/8 | 3.960 | 25 |

因此保留默认 4 槽。HTTP 请求数包含实际重试，不能把这些观测折算为模型 token 吞吐。

过载容量对照固定为 28 次突发提交、4 槽、截止 24 秒、每日 HTTP 响应延迟 2.5 秒。原截止仍包含排队；生产默认 300 秒未改动。

| 总容量 | 受理 / API 429 | 完整交付 | PARTIAL / FAILED | 未开始模型请求 | 从提交到终态 p95（秒） |
| --- | --- | --- | --- | --- | --- |
| 24 | 24 / 4 | 8/24 | 4 / 12 | 12 | 20.601 |
| 8 | 8 / 20 | 8/8 | 0 / 0 | 0 | 13.720 |

两组最终完整交付数量同为 8。默认容量收紧到 8 的取舍是少排队、更多请求直接收到 429，减少受理后超时；没有把拒绝算作成功，也没有声称提高总吞吐。完整交付与执行终态分别保留在 [原始观测](planning-load-20261022.json)，其中也保留最初失败；假模型参数不能推出真实供应商下的最佳容量。

繁忙恢复对照使用 1 槽、6 个新任务、每日日计划延迟 0.6 秒、截止 40 秒。第一天提交后终止原 worker，由另一个已繁忙的 worker 接管。`--scheduler baseline` 仅在实验子进程复现 `1bf4546` 的先领取、后按空槽扫描顺序，其余代码和参数相同。

| 调度顺序 | 接管前开始的新任务 | 从终止到接管首次 HTTP（秒） | 从终止到恢复交付（秒） |
| --- | --- | --- | --- |
| 历史顺序 | 6/6 | 11.851 | 12.775 |
| 空槽先恢复 | 2/6 | 4.148 | 5.047 |

两组均保留已完成天的条目 ID、原绝对截止和累计用量，6 个新任务也全部交付；跨 API 的 SSE 终态与详情一致。此处租约 3 秒、心跳 1 秒、轮询 0.1 秒，不能代替默认 90/30/1 秒配置的恢复时延。

组合边界检查：12 次提交、容量 8、4 槽、截止 20 秒；假供应商为每个受理任务的首次普通请求返回一次 429。8 个任务完整交付、4 次 API 429 拒绝、拒绝请求没有留下行程壳；实际收到 8 次供应商 429，经现有客户端重试完成。真实模型调用为 0。

失败同样保留：最初 12 秒压缩窗口中，容量 8 也只有 7/8 业务完整，其余为 PARTIAL；现有运行预算还预留 5 秒做终态收尾。后续一次过载复测还暴露了产品已终态而执行仍 live 的窗口，实验因等不到全部终态失败。现已修复持有者收尾及无持有者扫描，回归测试覆盖过期收尾和终态标题保留。

复现（后端目录，仍只对随机临时 MySQL 库操作）：

```bash
uv run python scripts/verify_planning_load.py --requests 12 --retry --deadline 20 --require-full --output /tmp/planning-load-burst.json
uv run python scripts/verify_planning_load.py --case recovery --concurrency 1 --deadline 40 --delay 0.6
uv run python scripts/verify_planning_load.py --case recovery --scheduler baseline --concurrency 1 --deadline 40 --delay 0.6
uv run python scripts/verify_planning_load.py --requests 28 --capacity 24 --delay 2.5 --deadline 24 --expect-expired
uv run python scripts/verify_planning_load.py --requests 28 --capacity 8 --delay 2.5 --deadline 24 --require-full
```

输出路径由调用者指定；Windows 可使用仓库外可写路径。CI 在迁移 job 中执行过载/429 与繁忙恢复两例，并上传 `planning-load-evidence` JSON。完整回归仍由 CI 执行。当前默认容量是保守的少排队策略，真实供应商时延、研究并行和富化成本仍需另行测量；多进程模型全局配额与跨主机可用性未在本阶段实现。
